## 1. 使用原则

本说明书用于将 GrandUMI 从当前阿里云中国香港正式服，安全迁移到新购的提速啦香港 CN2 服务器。新机规格为 8 核 8GB、75 Mbps、80GB 系统盘和 40GB XFS 数据盘；数据盘已经挂载到 `/data`。迁移采用新旧服务器并行方式，先部署和验证新机，最后才迁移生产数据并切换流量。

必须遵守：

1. 不在有活跃房间时重启后端、Caddy 或服务器。
2. 不直接购买任何按流量计费的高额公网或跨境加速产品。
3. 不在正式服直接进行容量压测。
4. 不把 8 核规格或 75 Mbps 套餐等同于容量认证。
5. 不一次性把房间上限从 400 提高到 600。
6. 不把密钥、Tunnel Token、数据库或备份提交到 Git。
7. 每个正式服代码版本必须先经过测试服和显式正式发布批准。
8. 新服务器验收、压测和临时域名验证期间，不修改旧正式域名，不影响旧服在线玩家。
9. 不把套餐中的 2 个公网 IP 当作双机或双线路高可用。

## 4. 新旧服务器只读检查

先在旧正式服务器记录当前基线：

```bash
date -Is
uptime
free -h
df -h
df -i
systemctl is-active grandumi-backend.service
systemctl is-active grandumi-frontend.service
systemctl is-active caddy

interface=$(ip -4 route show default | awk 'NR == 1 { print $5 }')
tc -s class show dev "$interface"
journalctl -u grandumi-network-monitor.service --since '-15 min' --no-pager -o cat
```

保存以下结果：

- 当前正式版本提交。
- 当前连接、玩家、房间和观战人数。
- 最近 15 分钟 CPU、内存、带宽、qdisc 和 TCP 重传。
- `/ready` 是否返回 200。
- 磁盘剩余空间。

再在新服务器记录硬件、挂载和网络基线：

```bash
date -Is
hostnamectl
nproc
free -h
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS
findmnt /data
df -h / /data
ip -br address
ip -4 route
systemctl is-active systemd-timesyncd
```

期望 `nproc` 为 8、内存约 8 GiB、`/dev/vdb1` 以 XFS 挂载到 `/data`。任一旧服服务异常或新机配置不符，都先排障，不开始生产迁移。

## 5. 不影响在线玩家的并行迁移原则

安装软件、部署代码、配置 `/data`、测试临时域名和执行隔离压测都只发生在新服务器，不需要重启旧服，也不会影响旧服在线对局。只有“最终生产数据同步”和“正式域名切流”需要维护窗口。

切流前按以下流程排空旧服：

1. 使用有权限的 GrandUMI 管理员账号登录旧正式服。
2. 在大厅维护控制面板点击“启动维护”。
3. 确认所有玩家看到维护提示，且新匹配、友谊房和约战均不能创建。
4. 观察维护面板中的活跃房间数并等待降为 0。
5. 在旧服确认连接和房间指标：

```bash
curl -fsS http://127.0.0.1:8080/metrics | grep -E '^grandumi_(connections|rooms|logged_in_players|spectators) '
```

6. 房间数不为 0 时禁止执行最终数据库同步或强制旧连接迁移。
7. 房间归零后执行 SQLite 在线备份、完整性校验和最终增量同步。
8. 先让新连接进入新服；已经保持健康 WebSocket 的旧连接不强制迁移。

DNS 切换不会主动搬迁已经建立的 WebSocket。旧服必须继续运行，直到旧连接自然结束或全部重连到新服。不得在切流后立即关机或释放旧服务器。

## 6. 迁移前数据保护

### 6.1 供应商快照与完整镜像

1. 在旧服务商控制台为旧正式服创建可用快照，并确认恢复方式。
2. 在提速啦控制台确认赠送的快照和完整镜像是否覆盖系统盘、数据盘，不能凭名称假设已经保护 `/data`。
3. 新机基础部署完成后创建一次新机基线快照，名称包含日期和版本，例如：

```text
grandumi-new-baseline-20260815-<commit前8位>
```

4. 等待快照状态变为完成并记录恢复入口。

注意：快照用于恢复系统或磁盘状态，不替代 SQLite 在线备份，也不替代实例外副本。

### 6.2 SQLite 在线备份

不能直接复制正在写入的 SQLite 主文件。应使用 SQLite 在线备份能力。实际数据库路径先从 systemd 环境或程序日志确认：

```bash
systemctl show grandumi-backend.service --property=Environment
journalctl -u grandumi-backend.service -b --no-pager | grep -E 'SQLite|玩家数据|排位|Leader'
```

对每个数据库分别执行备份，示例：

```bash
backup_root=/data/grandumi/backups/$(date +%F-%H%M%S)
install -d -m 0700 "$backup_root"
sqlite3 /data/grandumi/db/players.db ".backup '$backup_root/players.db'"
sqlite3 /data/grandumi/db/ranked.db ".backup '$backup_root/ranked.db'"
sqlite3 /data/grandumi/db/leader-stats.db ".backup '$backup_root/leader-stats.db'"
```

新服务器正式环境应使用上述 `/data/grandumi/db` 路径；从旧服导出时必须先读取旧服 systemd 环境并替换为旧服真实路径，不要盲目执行不存在的路径。

备份后验证：

```bash
sqlite3 "$backup_root/players.db" 'PRAGMA integrity_check;'
sqlite3 "$backup_root/ranked.db" 'PRAGMA integrity_check;'
sqlite3 "$backup_root/leader-stats.db" 'PRAGMA integrity_check;'
```

每个数据库都必须输出 `ok`。备份目录权限保持为 0700。

### 6.3 房间恢复日志

维护模式房间归零后，正常情况下不应有需要恢复的活动房间。仍需检查：

```bash
find /data/grandumi/persist -maxdepth 1 -type f -name '*.jsonl' -print
```

若仍有文件，不直接删除。先确认是否为异常残留，并与后端日志交叉检查。

## 7. 新服务器基础部署

新机部署不修改旧服，不需要等待旧服房间归零。按以下顺序执行：

1. 配置 SSH 密钥，验证密钥登录后再禁用 root 密码远程登录；在此之前保留控制台救援入口。
2. 候选环境使用仓库脚本安装 Git、curl、rsync、Nginx、.NET 10 和 Node.js 22；正式域名接入时可按架构切换为 Caddy/Cloudflare。
3. 创建程序与持久化目录：

```bash
install -d -m 0755 /opt/grandumi
install -d -m 0700 /data/grandumi/db
install -d -m 0700 /data/grandumi/persist
install -d -m 0700 /data/grandumi/backups
install -d -m 0750 /data/grandumi/logs
install -d -m 0750 /data/grandumi/replays
```

4. 后端正式 systemd 环境至少包含：

```ini
Environment=GRANDUMI_DATA_DIR=/data/grandumi/db
Environment=GRANDUMI_PLAYER_DB=/data/grandumi/db/players.db
Environment=GRANDUMI_RANKED_DB=/data/grandumi/db/ranked.db
Environment=GRANDUMI_PERSIST_DIR=/data/grandumi/persist
Environment=GRANDUMI_MATCH_LOG_DIR=/data/grandumi/logs/MatchLogs
Environment=GRANDUMI_REPLAY_DIR=/data/grandumi/replays
Environment=GRANDUMI_MAX_CONNECTIONS=1200
Environment=GRANDUMI_MAX_ROOMS=450
```

5. 应用仓库和发布产物放在 `/opt/grandumi`；数据库、WAL、房间恢复日志和备份不得写回代码目录。
6. 新机网络整形使用 systemd 主机专用覆盖，不修改旧服当前值：

```bash
install -d -m 0755 /etc/systemd/system/grandumi-network-tuning.service.d
printf '%s\n' '[Service]' 'Environment=GRANDUMI_EGRESS_RATE=60mbit' \
  > /etc/systemd/system/grandumi-network-tuning.service.d/override.conf
systemctl daemon-reload
```

7. 仓库基础单元的默认值已经从旧服临时 `2mbit` 修正为 `60mbit`；主机覆盖仍作为防误配的第二层保护。
8. 候选环境使用 `http://103.146.230.37` 和 `ws://103.146.230.37/ws`，暂不修改 `grand-umi.com`、`direct.grand-umi.com` 或本机 SSH 别名 `grandumi-hk`。
9. `deploy-hk.ps1` 仍只面向当前正式服。新机候选部署使用仓库根目录的 `deploy-new-hk-candidate.ps1`，脚本固定拒绝旧服 IP，并在 E 盘创建临时代码包。

首次候选部署命令：

```powershell
.\deploy-new-hk-candidate.ps1
```

脚本会依次完成代码包传输、基础依赖安装、60 Mbps 整形、systemd、Nginx、后端与前端构建，并从外网验证首页和 `/backend/ready`。候选部署不迁移生产数据库、不修改 DNS，也不构成正式发布批准。

## 10. Cloudflare Tunnel 旁路接入

Tunnel 必须先作为新服务器的新增测试线路接入，不能直接替换现有正式域名。

### 10.1 建议域名

```text
tunnel.grand-umi.com
```

### 10.2 接入原则

- `cloudflared` 安装在新服务器。
- Tunnel 指向本机 Caddy 或后端的受控本地地址。
- Tunnel Token 仅保存在服务器受限配置中。
- 不把 Token 写入仓库、脚本输出或聊天记录。
- 新域名先独立验证，不修改仍指向旧服的 `grand-umi.com` 和 `direct.grand-umi.com`。
- 同时验证 IPv4、IPv6、WebSocket 101、登录和短对局。

### 10.3 验证项目

```text
DNS -> TLS -> WebSocket 101 -> MsgSecret -> 登录 -> 进入房间 -> Ping -> 断线恢复
```

验证通过后，先在测试服客户端加入新端点，再经过正常正式发布流程。现有已经加载旧客户端的玩家不会被强制迁移；新加载客户端和以后重连的玩家才会使用新端点。

### 10.4 回滚

若 Tunnel 线路异常：

1. 从客户端候选端点中移除 Tunnel 域名。
2. 保留现有直连域名。
3. 不需要重启游戏后端。
4. 已连接到直连的玩家不受影响。
5. 停止 `cloudflared` 前先确认没有需要保留的 Tunnel 连接。

## 11. 低成本应用优化清单

以下优化应分别开发、测试和发布：

- [ ] 在线人数只在不同在线账号数真实变化时全服广播。
- [ ] 同账号连接替换只向新连接发送当前人数。
- [ ] 大厅状态合并到 500 ms～1 s 窗口。
- [ ] 按 `proto` 记录发送消息数和字节数。
- [ ] 记录完整快照与增量快照字节数和节省比例。
- [ ] 慢客户端触发重新同步而不是无限排队。
- [ ] 重连增加随机抖动和线路熔断。
- [ ] Tunnel 域名加入端点选择。
- [ ] 增加全局和单房间观战保护值。

每个前端 UI 变化必须验证 390×844 和 360×780 手机竖屏，以及对局页的横屏画布旋转结果。

## 12. 压测说明

### 12.1 隔离环境

容量压测不得连接正式服。使用独立测试实例、临时端口或 E 盘下的本地临时环境。GrandUMI 大体积临时产物只能放在 `E:\GrandUMI-Temp\`。

### 12.2 连接压测

现有脚本：[`tools/load/ws-soak.mjs`](../tools/load/ws-soak.mjs)

示例环境变量：

```powershell
$env:WS_URL='ws://127.0.0.1:8080/ws'
$env:CLIENTS='1600'
$env:DURATION_SECONDS='1800'
$env:CONNECT_BATCH='50'
node .\tools\load\ws-soak.mjs
```

### 12.3 建房压测

现有脚本：[`tools/load/match-soak.mjs`](../tools/load/match-soak.mjs)

```powershell
$env:WS_URL='ws://127.0.0.1:8080/ws'
$env:METRICS_URL='http://127.0.0.1:8080/metrics'
$env:CLIENTS='1300'
$env:DURATION_SECONDS='3600'
node .\tools\load\match-soak.mjs
```

该脚本主要验证登录、匹配、开局和保持，不能模拟完整真实操作。最终资格认证前必须增强脚本，使每个房间持续执行代表性的合法动作，并加入观战与重连风暴。

### 12.4 监控记录

压测期间每分钟保存：

- CPU、内存、GC 和线程池。
- 连接、玩家、房间、观战者。
- 房间和发送队列深度。
- 应用/持久化丢弃数。
- 出口 Mbps、qdisc drops/overlimits。
- TCP 重传和超时。
- 操作、快照和发送延迟 P50/P95/P99/Max。

### 12.5 通过条件

完整条件见架构文档第 15 节。任何消息丢弃、持久化丢弃、`/ready` 失败或持续 Swap 使用都判定为失败。新服务器还必须满足：出口 5 分钟平均不超过 45 Mbps、P95 不超过 55 Mbps，且 60 Mbps qdisc 没有持续丢弃。

## 13. 最终数据迁移、灰度切流与开放

### 13.1 切流前准备

1. 至少提前 24 小时把正式域名 TTL 降到 300 秒；只改 TTL，不改解析目标。
2. 使用临时域名完成管理员登录、友谊对局、出牌、聊天、投降、结算和断线重连。
3. 分别验证新机直连、Tunnel、IPv4，以及第二公网 IPv4（若计划使用）。
4. 确认新机 `/ready`、一分钟监控、60 Mbps qdisc 和 `/data` 写入都正常。
5. 在旧服开启维护模式并等待活跃房间归零。

### 13.2 最终生产数据同步

1. 在旧服使用 SQLite `.backup` 生成最终备份，不直接复制正在写入的数据库主文件或 WAL。
2. 对所有备份执行 `PRAGMA integrity_check;`，必须全部返回 `ok`。
3. 记录备份文件大小和 SHA-256；使用 `rsync`/`scp` 传到新机 `/data/grandumi/backups/<时间戳>/`。
4. 在新机验证 SHA-256 一致，再停止新机测试后端并将备份恢复到 `/data/grandumi/db`。
5. 按服务运行用户修正目录所有者和 0600/0700 权限，启动新机后端。
6. 核对玩家、卡组、排位和 Leader 数据抽样，并再次检查 `/ready` 与日志。

迁移期间旧服保持维护模式，禁止旧服和新服同时接受会写入长期数据的正式玩家，避免形成两份不可自动合并的数据库。

### 13.3 灰度切流

1. 先让管理员和少量测试账号通过正式候选端点连接新机。
2. 验证一场完整对局、重连、观战和结算，同时观察至少 15 分钟。
3. 更新客户端端点优先级或正式域名解析，使新连接优先进入新服务器。
4. 不主动断开仍连接旧服的健康 WebSocket；旧服继续运行但保持禁止新建房间。
5. 监控旧服连接数自然归零，并确认所有新连接都进入新服。
6. 新服稳定 30 分钟后关闭旧服维护提示，宣布迁移完成；持续重点观察 24 小时。
7. 旧服务器至少保留 7 天，不立即关机、重装或释放公网 IP。

正式开放后先维持 1,200 连接/450 房间保护值。未完成相应容量压测前，不提高到下一阶段。

## 15. 常见故障处理

### 15.1 网页能打开但一直重连

1. 不重启服务器。
2. 分别探测直连和 Tunnel 的 WebSocket 101。
3. 检查 IPv4 和 IPv6 差异。
4. 检查后端 `/ready` 和持续日志。
5. 后端正常而单路径失败时，降低该端点优先级。
6. 提醒玩家切换网络并等待自动恢复，不强制刷新正在对局页面。

### 15.2 CPU 持续超过 75%

1. 开启维护模式，停止新对局。
2. 检查房间数、观战数和重连速率。
3. 检查操作延迟、快照构建和广播指标。
4. 不立即重启；让现有房间自然结束。
5. 找出异常协议或房间后再处理。

### 15.3 出口持续超过 55 Mbps

1. 检查按协议字节数。
2. 检查完整快照比例和观战人数。
3. 检查在线人数/大厅广播是否异常放大。
4. 检查 TCP 重传是否使实际流量增加。
5. 开启维护模式限制新增房间，但不打断现有房间。
6. 不直接解除或提高 60 Mbps 整形；优先限制新房间、观战和完整快照放大。

### 15.4 应用消息丢弃增长

1. 立即停止提高容量。
2. 检查慢客户端和发送队列。
3. 确认丢弃的是可重建状态还是关键消息。
4. 关键消息发生丢弃时进入维护模式。
5. 保留日志和指标用于复盘。

### 15.5 磁盘超过 80%

1. `/data` 达到 75% 时开启维护模式，防止新房间继续产生日志。
2. 分别确认 `/` 与 `/data` 的大目录和增长来源。
3. 先转移并归档历史日志，不删除未知文件。
4. 不删除 SQLite WAL、活动房间 JSONL 或当前发布目录。

### 15.6 后端进程崩溃

1. systemd 应自动重启服务。
2. 检查 `/live`、`/ready` 和房间恢复日志。
3. 不反复手工重启。
4. 收集崩溃前后 journal、OOM、磁盘和 TCP 指标。
5. 恢复失败时开启维护模式并按备份恢复流程处理。

## 16. 回滚原则

### 16.1 代码回滚

- 只通过现有版本化发布流程回滚。
- 保留上一版前后端发布目录。
- 后端未就绪时恢复上一发布产物。
- 不使用 `git reset --hard` 覆盖正式服务器数据。

### 16.2 容量参数回滚

出现资源压力时按相反顺序回退：

```text
1600/600 -> 1400/550 -> 1200/450 -> 1000/400
```

参数回滚仍需要后端重启，必须等待活跃房间归零。

### 16.3 新服务器迁移回滚

若正式切流前或尚未产生新服生产写入时发现异常：

1. 立即停止扩大灰度，保持旧服运行。
2. 将客户端端点优先级或 DNS 恢复到旧服。
3. 保持新服隔离，收集日志、qdisc、TCP 和应用指标。
4. 不需要重启仍在旧服的健康对局。

若新服已经产生玩家资料、卡组、排位或结算写入，不得直接把 DNS 指回旧服后继续营业，否则会造成数据回退或分叉。必须重新进入维护模式、排空新服房间，对新服 SQLite 做在线备份和完整性校验，再决定反向迁移到旧服或修复新服后继续运行。

## 17. 安全要求

- SSH 禁止密码弱口令，优先密钥登录。
- 防火墙只开放 80、443 和受限来源 SSH。
- SSH 密钥验证成功并保留控制台救援入口后，禁用 root 密码远程登录。
- Kestrel 只监听 `127.0.0.1`。
- `/metrics` 不直接暴露公网。
- Tunnel Token 和数据库备份权限为 0600/0700。
- 管理维护权限只授予明确账号。
- 定期更新 Ubuntu、Caddy、.NET Runtime 和 `cloudflared`，但更新必须走维护排空流程。
- 日志中不得记录密码、Token 或完整认证信息。
