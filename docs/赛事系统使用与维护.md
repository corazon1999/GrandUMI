# 赛事系统使用与维护

## 举办与参赛

大厅新增“赛事”入口。玩家申请时填写名称、人数、卡池、报名时间、开赛时间、奖励说明，以及赛事管理员和裁判账号。人数支持8、16、32、64、128、256。平台管理员在“管理面板 → 内容管理 → 打开赛事管理”或赛事大厅待审核分类中审核，通过后公开。

已取消赛事仅举办者、该赛事管理员、裁判和平台管理员可查看。普通玩家及原参赛者的赛事列表不再显示这些赛事，也不能直接读取详情。

赛事管理员、裁判必须独立于参赛者。举办者可以安排其他账号担任工作人员后参赛。奖励说明仅作展示，系统不自动发放奖励。

参赛者选择已保存的云端卡组报名，满额进入候补。开放报名后，已报名玩家即可提前签到，无需等待开赛前30分钟。签到时必须二次确认“签到后退赛扣15信誉分”；正选与候补均适用。签到后及开赛后仍可主动退出，退赛须再次确认本次扣分与扣后分数。未签到退出不扣分。已被淘汰的选手已完成参赛，不再提供退赛操作。报名截止前仍可更新卡组，更新卡组或举办者修改申请并重新审核均保留已确认的签到。

计划开赛前5分钟自动释放未签到正选，并按报名顺序补入已签到候补。举办者或赛事管理员可随时开启首轮，不受原计划时间及满员限制，至少需要2名有效签到选手。二次确认中显示实际人数、轮数与晋级人数；确认后按报名顺序纳入已签到选手（含候补递补，至多申请容量），立即关闭报名、卡组修改和签到。赛程及实际开赛时间会持久化，后续退赛不改变既定瑞士轮轮数。

在首轮前，举办者或赛事管理员可以单独提前或推迟计划开赛时间，并同步调整报名截止时间，填写原因后通知在线相关人员；无需重新审核，保留已签到和卡组。报名截止仍须早于计划开赛至少5分钟。计划时间已到但首轮尚未开启时，有效报名选手仍可签到；被释放的未签到名额需在新的报名窗口重新报名。

举办者或赛事管理员可在参赛名单管理中移出选手或代办退赛，必须填写原因。移出原因向玩家展示并保存审计记录，被移出者不能重新报名本场赛事；举办者单方面移出不自动扣信誉分。代办退赛仅用于选手明确要求退赛的情形，已签到者同样扣15分，并须确认。参赛中的举办者不能处理自己或自己尚未结束比赛桌的对手，须由独立管理员操作。未完成桌判仍有效的对手胜，双方均退出时瑞士轮双败、淘汰赛空桌；已完成战绩保留。若已进入主动结束后的人工结算阶段，退赛与移出不跳过全桌人工确认。

赛事中的举办者、工作人员、参赛名单、赛程对阵、积分排名、冠军、逐桌结算、申诉与操作记录均在姓名旁以较小字号显示当前绑定QQ。赛事牌桌及观战中的姓名同步显示QQ，离开对应赛事房间后不带入普通对局。联系信息按账号匹配，未绑定显示“未绑定QQ”；历史重名时在牌桌提示到赛事对阵中核对，不猜测QQ归属。

## 对阵、轮次和成绩

每桌双方分别落座后独立开局，决赛默认不限时，其余对局默认30分钟。到时只提醒本赛事的举办者、管理员和裁判，比赛继续，不自动判负、进入追加回合或随机决胜；是否双败以及何时结算由管理员人工决定。公布对阵5分钟后仍未落座的桌转为待处理并提醒工作人员，不自动判负，之后仍可重新落座。

赛事管理员可在“赛事管理 → 单桌计时与人工判定”中单独调整某桌剩余时间（1至1440分钟），或设为不限时；未开局桌调整的是开局时长。每次调整必须填写原因，保存截止时间、操作人和审计记录，并通知本桌选手及工作人员。延长时间后按新的截止时间重新提醒，重复扫描或重启不会重复记录同一次超时；离线工作人员重新进入时可从顶部超时提醒和单桌状态继续处理。管理员不能调整或判定自己所在的桌，普通选手、裁判和仅举办者身份不能调整对局计时。

管理员可在比赛继续进行时，直接为单桌选择甲方胜、乙方胜或双方判负，填写原因后只结束该桌。淘汰赛人工双败不产生胜者，空签位沿原签表递进；全部选手均被淘汰或决赛双方判负时可无冠军结束。其他桌照常进行，未全部结算前不能开下一轮。

管理员自行选择下一轮开始时间。主动结束瑞士轮须填写原因并二次确认，随后所有桌均转入人工确认，包括已自然结束的桌；原结果作为参考保留。每桌必须明确选择胜负或双败并填写说明。全桌结果确认、未决申诉处理完后才能开启下一轮。裁判改判同样需要说明，已完成赛事不允许改写结果。

瑞士轮默认不重复交手，确实无法配对时须确认必要重复并填写裁判说明。胜与轮空各1分，负和双败0分，按积分、对手胜率、对手的对手胜率、固定抽签顺序排名。满员时瑞士轮轮数依次为3、4、5、6、7、8轮；晋级人数依次为4、4、8、8、8、16人。未满员时，瑞士轮轮数为实际开赛人数以2为底对数向上取整，晋级人数取原规格晋级数与不大于实际开赛人数的最大二次幂中的较小值（例如3人：2轮后2强；7人：3轮后4强；10人：4轮后4强）。随后固定种子单败淘汰，不设季军赛。

每轮仅为仍在参赛的选手配对。人数为奇数时自动产生一桌轮空，直接确认轮空胜并计1分；优先安排轮空次数少、积分低的选手，必要时尝试其他轮空人选以避免重复交手。中途退出及移出均保留历史积分，下一轮不再配对该选手。所有桌结算且无未决申诉后，只剩1名有效选手时，由管理员推进并确认其为冠军；瑞士轮无人继续参赛时应取消赛事；淘汰赛因人工双败无人晋级时记为已结束且不产生冠军。

赛事对局不计排位。观战固定隐藏双方手牌，单桌结束仍隐藏；赛事整体结束后才能公开分享赛事回放。选手断线使用每桌累计120秒宽限。

## 赛事信誉

每个账号初始100分，范围0至100分。签到后主动退赛或由工作人员代办退赛，每次扣15分（不足15分时扣至0）；未签到退赛、工作人员单方面移出、赛事取消不扣分。

正常完成赛事时，仍有效或已正常淘汰、且至少参加过一桌有明确胜者的非轮空对局的选手，加5分，封顶100；退赛、被移出以及只有轮空或双败记录者不获奖励。奖励在整场赛事完成时入账，重复保存、重启与请求重试不会重复加减分。当前版本不按信誉分限制报名。报名签到页显示自己的分数与最近20条明细。分数与流水和赛事状态在同一SQLite事务内保存。

## 固定测试账号

测试服预置`test01`至`test16`，密码统一为`123456`，无需绑定QQ，可同时使用16个独立账号验证赛事。它们没有平台管理员权限，固定密码不支持修改或重置；举办及审核操作由原有具备权限的账号执行。

此功能只在`hk-test-01`节点设置`GRANDUMI_FIXED_TEST_ACCOUNTS=1`时启用，凭证和会话独立保存在测试数据目录的`fixed-test-accounts.db`，不向共享账号库创建这些身份。群成员白名单刷新不会移除这些固定账号。若同名共享账号已存在或节点配置不符，启动会拒绝覆盖并报告原因。普通账号仍执行原有密码长度和QQ准入规则。

## 存储与恢复

`tournaments.db`位于玩家数据库同目录，SQLite事务保存赛事配置、报名及卡组快照、轮次、桌次、逐桌确认、申诉、审计和幂等请求记录。备份时应与玩家数据库、房间恢复日志及云回放保持一致，运行中采用SQLite在线备份或停写备份，勿只复制主库而遗漏WAL。

赛事审核锁定规则版本及摘要。恢复时按原规则重建房间；规则缺失、账号离线或房间冲突会显示待处理，管理员或裁判需核查。不会静默换规则或自动跳过未结算桌。主动结束及人工双败采用可恢复的中立终局日志，迟到的自然结果不能覆盖人工确认。赛事房间不受普通房间30分钟无操作清理及恢复期限限制，确保不限时决赛和等待人工处理的对局可继续与恢复。

赛事RPC为`MsgTournament`，按`requestId`匹配响应，写操作携带`revision`，服务端重新校验权限及权威状态；`MsgTournamentClock`同步每桌时间，`MsgTournamentNotice`向在线相关人员提示审核、开轮、公告及结束，并向赛事工作人员提醒超时；单桌计时变更与人工裁定仅通知本桌选手和工作人员。离线玩家重新进入后读取持久状态和公告。

## 验证入口

服务端专项：`dotnet test 服务端WebSocket.Tests/GrandUMIServer.Tests.csproj --filter FullyQualifiedName~Tournament`，使用项目提供的E盘测试临时目录。

完整验证：`verify.ps1`。开启布局验证环境变量后，`/layout-verification/tournaments`提供真实赛事管理界面；`?view=manual`验证逐桌结算，`?view=game`验证赛事对局时钟及竖屏旋转。部署使用标准`deploy-test.ps1`并校验测试服外网HTTP。
