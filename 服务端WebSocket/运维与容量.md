# GrandUMI 服务端容量与稳定性基线

更新日期：2026-08-26

## 结论

本轮验证所在主机为 20 逻辑处理器、约 31.6GB 内存、NVMe 磁盘。单进程服务端已经通过以下本机回环验证：

| 场景 | 结果 | P95 / 资源 |
|---|---:|---:|
| 500 个 WebSocket 在线连接，持续心跳 | 500/500 成功，0 掉线，0 丢包 | 心跳 RTT P95 18.12ms |
| 1000 个 WebSocket 在线连接，持续心跳 | 1000/1000 成功，0 掉线，0 丢包 | 心跳 RTT P95 52.39ms |
| 200 名玩家、100 个真实对局 | 全部完成登录、匹配、先后手和调度手牌 | 工作集约 144MB，四类队列 0 丢弃 |
| 500 名玩家、250 个真实对局 | 全部进入稳定对局并正常结算 | 工作集约 197MB，四类队列 0 丢弃 |
| 1000 名玩家、500 个真实对局突发建房 | 全部进入稳定对局并正常结算 | 约 52 秒全部就绪；工作集约 283MB，四类队列 0 丢弃 |
| 500 个房间同时结束后的清理风暴 | 房间归零，健康检查继续响应 | `/ready` 约 92ms，0 过载、0 丢弃 |

因此，当前版本可采用以下口径：

- 已验证的同时在线连接数：1000。
- 已验证的同时对局玩家数：1000（500 个房间）。
- 单节点建议生产准入：最多 1000 个连接、400 个房间；也就是最多约 800 名玩家同时打牌，并为大厅、观战、重连和流量波动保留约 20% 余量。
- 单节点本轮验证上限：1000 名玩家同时打牌（500 个房间）。这不是破坏性极限；在未完成公网混合流量长稳压测前，不建议继续提高承诺容量。

公网玩家延迟还包含玩家到部署地域、Cloudflare/Caddy、运营商线路的 RTT。本机回环数据用于判断服务端排队和吞吐，不代表公网端到端延迟。

## 本轮落地的五部分

### 1. 网络与协议背压

- WebSocket 改为 Kestrel 承载，限制连接数、升级连接数、请求头等待和请求体大小。
- 每个连接只有一个有界发送队列，最多 256 条；状态、在线人数和玩家列表可原位合并。
- 关键协议不能静默丢失。关键消息积压到上限时主动断开慢连接，避免客户端与权威状态长期分叉。
- 入口使用连接级令牌桶；聊天、玩家列表另有限频，聊天长度限制为 200 字符。
- 在线人数改为 500ms 合并广播，玩家列表改为最多 200 条分页响应，前端不再每 4 秒轮询。
- 同账号重连时，账号索引切换与旧会话失权原子完成；在线人数和玩家列表只读取唯一权威会话。旧连接即使不响应关闭，也会在 2 秒有界窗口后强制中止，且其迟到清理不会误删新连接索引。
- 匹配取消使用墓碑跳过，避免高峰期反复重建队列造成平方级开销。
- 游戏状态支持协商式增量快照；旧客户端继续接收完整快照。

### 2. 执行与持久化

- 房间动作继续使用单房间单读者队列，不同房间可并行，单局内保持确定顺序。
- 录像、训练日志和恢复日志使用有界后台批量 JSONL 写入，正常关服会排空队列。
- 恢复日志不再为每个房间持有 `AutoFlush` 文件流，降低大量房间时的句柄和同步磁盘写入压力。
- 重复登录的 `last_login_at` 写入按玩家合并，每 5 秒批量事务落库；新账号仍同步创建。
- Leader 排行榜聚合结果缓存 15 秒，新对局写入时失效，避免每次打开页面都扫描统计表。
- `GRANDUMI_DATA_DIR` 现在统一承载玩家库、录像、对局日志和恢复日志；也可分别覆盖目录。

### 3. 过载保护与可观测性

- `/live`：进程存活。
- `/ready`：网关已接流且未触发连接、房间、内存或持久化积压保护。
- `/version`：版本、提交、构建时间和节点标识。
- `/metrics`：Prometheus 文本，包含处理器进程、GC、线程池、连接、登录会话、唯一账号、待清理替代会话、房间、队列深度、丢弃数和累计延迟直方图。
- `GRANDUMI_MAX_CONNECTIONS` 和 `GRANDUMI_MAX_ROOMS` 控制准入；达到上限时新握手或新建房间会收到过载响应，已有对局继续运行。

建议告警：

- 任意 `*_dropped_total` 增长：立即告警。
- WebSocket 当前最大队列深度持续超过 128：高优先级告警。
- 房间动作队列非零持续 30 秒，或“动作接收到房间出队”P95 超过 50ms：高优先级告警。
- 服务端每分钟扫描一次权威房间池：已终局但残留的房间立即回收，连续 30 分钟没有有效操作的房间自动关闭并清理。启动恢复也使用相同的 30 分钟口径，避免死房间长期占用容量或阻塞维护排空。
- 任一持久化队列超过容量 50% 持续 1 分钟：高优先级告警。
- `/ready` 返回 503 或 `grandumi_overloaded=1`：摘除节点并告警。
- 工作集超过容器/主机限制的 75%，或线程池忙线程持续升高：容量预警。
- `grandumi_superseded_sessions` 持续非零超过 10 秒：高优先级告警，表示旧连接未按 2 秒回收预期退出；`grandumi_superseded_sessions_total` 短时陡增表示发生重复登录或重连风暴。

连接与在线指标口径：

- `grandumi_connections`：仍登记在进程内的全部 WebSocket 连接，包括未登录连接和正在回收的旧连接。
- `grandumi_logged_in_sessions`：已带账号身份的会话数，包含已经被替代但尚未完成清理的旧会话，用于诊断重复会话积压。
- `grandumi_logged_in_players`：兼容既有看板的在线玩家指标，现按账号索引中的唯一权威会话统计。
- `grandumi_unique_logged_in_accounts`：与在线玩家相同的明确口径指标，推荐新看板使用。
- `grandumi_superseded_sessions`：已经失去账号权威、正在终止或等待清理的会话数；正常情况下应迅速回到 0。

## 推荐配置

测试服当前只有 50% CPU、768MB 内存限制，配置为 300 个连接、100 个房间。生产单节点在完成公网压测前建议从以下配置起步：

```text
GRANDUMI_NODE_ID=production-01
GRANDUMI_MAX_CONNECTIONS=1000
GRANDUMI_MAX_ROOMS=400
GRANDUMI_PRIVATE_SNAPSHOT_LOG=0
GRANDUMI_PROTOCOL_LOG=0
GRANDUMI_DATA_DIR=<独立持久化目录>
```

容量调整遵循“小步上调”：观察一周 P95/P99、队列、GC、工作集和丢弃数，再按 20% 幅度增加。默认的 1000 连接、400 房间已经保留余量；不要在未压测时直接上调。

## 多节点扩展边界

代码已经抽象 `IRoomPlacementDirectory`，当前实现是单进程本地目录。真正横向扩展还需要：

1. 用 Redis 或数据库实现共享房间目录和节点心跳。
2. 入口按账号或房间做一致性路由；对局建立后保持 WebSocket 粘性。
3. 邀请、匹配和大厅在线状态从进程内字典迁移到共享协调层。
4. 房间仍由单节点单写，跨节点只做路由，不做同一房间多主写入。
5. 节点进入不就绪后停止新房，等待已有房间自然结束，再发布或下线。

在以上协调层完成前，只能运行一个权威游戏节点；多开进程会形成互相不可见的匹配队列和房间状态。

## 验证命令

```powershell
# 纯连接与心跳
$env:WS_URL='ws://127.0.0.1:8080/ws'
$env:CLIENTS='1000'
node .\tools\load\ws-soak.mjs

# 完整对局房间
$env:METRICS_URL='http://127.0.0.1:8080/metrics'
$env:CLIENTS='500'
node .\tools\load\match-soak.mjs
```

正式扩容验收至少需要 30 分钟稳态、真实公网入口、符合线上比例的大厅/对局/观战混合流量，并且所有丢弃计数保持为 0。
