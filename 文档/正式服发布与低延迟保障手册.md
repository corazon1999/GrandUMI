# GrandUMI 正式服发布与低延迟保障手册

- 适用范围：GrandUMI 测试服验证、正式服批准、北京时间零点自动发布、紧急发布和发布后故障处置
- 最后更新：2026-08-13
- 依据：2026-08-11、2026-08-12 正式服发布后的高延迟事故及修复验证

## 1. 这份手册解决什么问题

正式服发布不能只以“构建成功”“服务进程存活”或“首页 HTTP 200”为成功标准。2026-08-11 和 2026-08-12 的两次事故说明，网页仍能打开时，对局 WebSocket 也可能已经进入秒级延迟；静态资源链路配置不当还可能造成首页空白、更新日志不刷新或新旧资源混用。

本手册把以下内容设为正式发布的硬性门禁：

1. 发布候选必须是已经部署并验证过的测试服提交。
2. 正式服必须优先连接香港 WebSocket 直连线路，Cloudflare 只作为故障兜底。
3. Next.js 运行所必需的 JS/CSS 必须保持主站同源；卡图等大体积公共资源走独立静态资源域名。
4. 源站网络保护必须处于启用状态，静态资源预热必须限并发、限速。
5. 发布后必须检查真实 WebSocket 端点和对局延迟，不能只检查 HTTP 状态码。

## 2. 两次事故与最终经验

### 2.1 2026-08-11：静态资源与对局流量互相争抢

#### 现象

- 卡牌图鉴、卡背和网页资源集中加载时，网页明显变慢。
- 大量静态资源占用源站出口后，WebSocket 心跳和对局操作一起变慢。
- 服务器重启或重新部署后，临时网络优化可能丢失。
- 如果无节制地预热大量卡图，预热本身也会挤占在线玩家带宽。

#### 根因

- 大体积、可缓存的静态资源与实时对局通信共用源站链路。
- 跨境链路出现拥塞和丢包时，TCP 反复退避，延迟被放大。
- 网络队列、拥塞控制和 MTU 探测没有完整持久化。

#### 成功修复

- 卡图、卡背等公共资源使用 `https://assets.grand-umi.com`。
- 静态域由 Caddy 只读提供可缓存资源，自定义卡背按专用路径代理到后端。
- 持久启用 BBR、TCP MTU 探测、HTB 出口整形和 fq 队列。
- 发布预热默认单并发、单请求 `128 KB/s`，避免缓存填充拖慢在线对局。

### 2.2 2026-08-12：紧急发布绕过新配置，WebSocket 走高延迟线路

#### 现象

- 紧急发布后登录和对局操作出现极高延迟。
- 网页可能继续引用旧脚本，更新日志不能及时刷新。
- 随后的资源分流调整一度让首页刷新后只剩背景和设置按钮。

#### 根因

- 旧紧急发布入口构建前端时没有携带完整的生产环境变量，导致正常发布与紧急发布产物不一致。
- 正式服主域优先使用 Cloudflare WebSocket，而当时该线路持续心跳 P95 为 `1372.2 ms`；香港直连线路 P95 只有 `14.0 ms`。
- 首页 HTML 被共享缓存长期复用，发布后仍可能引用旧版本资源。
- 最初把 Next.js 关键 JS/CSS 也切到独立静态域，静态域不可达或缓存版本不一致时，页面主体无法启动。

#### 成功修复

- 正式服 WebSocket 固定为 `wss://direct.grand-umi.com/ws` 优先，`wss://grand-umi.com/ws` 仅作兜底。
- 正常发布和紧急发布都必须带上相同的生产构建变量：

  ```text
  NEXT_PUBLIC_WS_URL=wss://grand-umi.com/ws
  NEXT_PUBLIC_ASSET_ORIGIN=https://assets.grand-umi.com
  CARD_BACK_API_URL=http://127.0.0.1:8080
  ```

- 首页改为动态响应，发布后不复用长期缓存的版本入口 HTML。
- Next.js 关键 JS/CSS 恢复主站同源；卡图等大体积公共资源继续走独立静态域。

## 3. 当前不可破坏的正式服架构

| 流量 | 当前主线路 | 备用或约束 |
| --- | --- | --- |
| 首页和 Next.js JS/CSS | `https://grand-umi.com` 同源 | 不得通过 `assetPrefix` 整体迁移到静态域 |
| 卡图、精灵图等公共资源 | `https://assets.grand-umi.com` | Caddy 只开放允许的静态路径 |
| 自定义卡背 | `assets.grand-umi.com/card-back-images/*` | 由 Caddy 代理到正式服后端 `127.0.0.1:8080` |
| 对局 WebSocket | `wss://direct.grand-umi.com/ws` | `wss://grand-umi.com/ws` 仅为 Cloudflare 故障兜底 |
| 正式服后端 | `127.0.0.1:8080` | 必须通过 `/ready` 和 `/version` 验证 |
| 正式服前端 | `127.0.0.1:3000` | 由 Caddy 对外提供主站服务 |

任何发布脚本、Next.js 配置、Caddy 配置或 WebSocket 端点调整，只要改变上表，就必须视为高风险网络变更，重新完成本手册中的全部回归与公网验证。

## 4. 正常发布流程

### 4.1 发布候选的前置条件

发布前必须同时满足：

- 当前分支是 `main`。
- 本次任务相关代码已经通过对应测试。
- 每项已完成修复均已写入 `changelog-cache/pending/`。
- 工作区中的无关改动已经识别并排除，不能夹带提交。
- 所有需要正式发布的待发布记录已经汇总到 `opcgpro-web/src/data/changelog.ts`。
- 已汇总的记录已经移动到 `changelog-cache/published/<版本号>/`，没有静默删除。
- 最终发布候选提交已重新部署到测试服，并完成测试服实际验证。

先检查分支和文件边界：

```powershell
git branch --show-current
git status --short
git diff --name-only
git diff --cached --name-only
```

禁止使用 `git add -A` 或 `git add .`。只暂存本次发布涉及的明确文件：

```powershell
git add -- <文件1> <文件2> <更新日志记录>
git diff --cached
git commit -m "feat: 发布<版本号>更新"
```

> `deploy-test.ps1 -Commit` 和 `deploy-hk.ps1 -Commit` 在脏工作区中会执行全量暂存。存在任何无关改动时禁止使用这两个自动提交参数，必须先手工按文件边界提交。

### 4.2 发布链路专项回归

凡涉及前端、网络、域名、缓存、Caddy 或部署脚本，至少运行：

```powershell
Push-Location .\opcgpro-web
node --test tests/cdn-asset-routing.test.mjs tests/ws-endpoint-fallback.test.mjs
Pop-Location
```

正式服环境变量下的前端构建验证：

```powershell
Push-Location .\opcgpro-web
try {
  $env:NEXT_PUBLIC_WS_URL = "wss://grand-umi.com/ws"
  $env:NEXT_PUBLIC_ASSET_ORIGIN = "https://assets.grand-umi.com"
  $env:CARD_BACK_API_URL = "http://127.0.0.1:8080"
  npm run build
} finally {
  Remove-Item Env:NEXT_PUBLIC_WS_URL -ErrorAction SilentlyContinue
  Remove-Item Env:NEXT_PUBLIC_ASSET_ORIGIN -ErrorAction SilentlyContinue
  Remove-Item Env:CARD_BACK_API_URL -ErrorAction SilentlyContinue
  Pop-Location
}
```

此外必须运行改动本身对应的前端、后端或端到端测试。UI 改动还要按项目规范检查电脑端、`390×844` 和 `360×780` 手机竖屏；对局页需要验证竖屏设备自动旋转后的横屏画布。

### 4.3 部署并验证测试服

工作区干净、提交边界正确后运行：

```powershell
.\deploy-test.ps1
```

脚本成功并且 `https://test.grand-umi.com/` 返回 HTTP 200，才表示代码已进入测试服，但这仍不等于可以批准正式发布。

测试服至少验证：

1. 登录、进入大厅、匹配或房间码建房正常。
2. 完成一段真实对局操作，确认提示、出牌和状态同步没有异常等待。
3. 普通刷新和无痕窗口首次访问都能正常显示首页，不出现只有背景的空白页。
4. 更新日志显示本次正确版本和内容。
5. 卡图、卡背及本次新增资源均能加载。
6. 若发布候选又有任何改动，必须重新提交、重新部署测试服并重新验证。

### 4.4 批准正式发布

确认当前测试服部署的就是最终候选后运行：

```powershell
.\approve-release.ps1
```

该命令只批准当前测试服提交，不会立即更新正式服。服务器会在北京时间下一个 `00:00` 自动发布。

批准后应记录脚本输出的完整提交号。也可核对服务器状态：

```powershell
ssh root@8.210.155.25 "cat /var/lib/grandumi-release/test-deployed"
ssh root@8.210.155.25 "cat /var/lib/grandumi-release/approved"
```

两者必须是同一个 40 位提交号。批准后如果又部署了新的测试服提交，自动发布会因“批准版本与当前测试服版本不一致”而停止；此时必须重新验证并重新批准，不能绕过校验。

### 4.5 零点自动发布行为

- `grandumi-production-promote.timer` 在北京时间每天 `00:00` 触发。
- 如果正式服仍有 WebSocket 连接，脚本每 5 分钟检查一次，最多等待一小时。
- 一小时后仍有玩家在线，会跳过当晚发布，不会强制断线。
- 发布只接受测试服已经部署、明确批准、属于 `origin/main` 且是当前正式服后继的提交。
- 后端或前端启动失败时，脚本会尝试恢复旧构建。
- 静态资源预热失败只会记录警告，不会为了预热失败中断已经正常运行的正式服务。

发布窗口应观察：

```powershell
ssh root@8.210.155.25 "systemctl status grandumi-production-promote.service --no-pager"
ssh root@8.210.155.25 "journalctl -u grandumi-production-promote.service -n 200 --no-pager"
```

日志中只有出现“正式服发布成功：<提交号>”，并通过第 5 节全部验证后，才能宣布发布完成。如果日志显示“仍有玩家”“跳过本次发布”或任何错误，均不得声称已经发布。

## 5. 发布后强制验收

### 5.1 版本和服务状态

```powershell
ssh root@8.210.155.25 "cat /var/lib/grandumi-release/production-deployed"
ssh root@8.210.155.25 "systemctl is-active grandumi-backend.service grandumi-frontend.service caddy grandumi-network-tuning.service"
ssh root@8.210.155.25 "curl -fsS http://127.0.0.1:8080/ready && curl -fsS http://127.0.0.1:8080/version"
```

验收标准：

- `production-deployed` 等于批准的完整提交号。
- 后端、前端、Caddy 和网络保护服务均为 `active`。
- `/ready` 成功，`/version` 包含批准提交号。

### 5.2 公网 HTTP 和静态资源

```powershell
curl.exe --noproxy "*" -sS -o NUL -w "首页 HTTP=%{http_code} 总耗时=%{time_total}s`n" -L https://grand-umi.com/
curl.exe --noproxy "*" -sS -o NUL -w "静态资源 HTTP=%{http_code} 总耗时=%{time_total}s`n" https://assets.grand-umi.com/sprites-thumb/CardBack.webp
```

浏览器开发者工具中还必须确认：

- 页面关键 `/_next/static/*.js` 和 `*.css` 从 `grand-umi.com` 同源加载。
- 卡图、精灵图等大体积资源从 `assets.grand-umi.com` 加载。
- 普通刷新和无痕窗口首次打开均无首页空白。
- 更新日志是本次版本，不是旧缓存内容。

### 5.3 WebSocket 线路与真实延迟

这是最重要的发布验收，不能用 HTTP 200 替代。

1. 打开 `https://grand-umi.com`，在浏览器开发者工具的“网络 / WS”中查看实际连接。
2. 首选连接必须是 `wss://direct.grand-umi.com/ws`。
3. `wss://grand-umi.com/ws` 只允许在直连入口确实无法使用时作为兜底；发布后无故直接走该线路视为未通过。
4. 登录并进行真实对局操作，观察浏览器控制台中的 `[延迟] WebSocket RTT` 和操作往返日志。
5. 至少覆盖登录握手、进入大厅、开始对局、连续多次操作和一次重连。

历史基线是香港直连持续心跳 P95 `14.0 ms`，事故时 Cloudflare 主线路 P95 `1372.2 ms`。验收时应使用同一网络环境与发布前测试对照：

- P95 相比发布前明显翻倍或持续增加超过约 `50 ms`，先停止宣布成功并调查。
- 持续超过 `300 ms` 属于明显异常。
- 接近或超过 `1 s` 直接按发布事故处理。
- 个别瞬时尖峰不能单独定性，应结合持续样本、实际端点和操作往返共同判断。

### 5.4 源站网络保护

```powershell
ssh root@8.210.155.25 "sysctl net.ipv4.tcp_congestion_control net.ipv4.tcp_mtu_probing"
ssh root@8.210.155.25 "systemctl is-enabled grandumi-network-tuning.service && systemctl is-active grandumi-network-tuning.service"
ssh root@8.210.155.25 "tc qdisc show"
ssh root@8.210.155.25 "caddy validate --config /etc/caddy/Caddyfile"
```

预期结果：

- TCP 拥塞控制为 `bbr`。
- `net.ipv4.tcp_mtu_probing = 2`。
- 根队列包含 HTB，子队列包含 fq。
- `grandumi-network-tuning.service` 为 `enabled` 且 `active`。
- Caddy 配置验证通过。

## 6. 紧急发布流程

### 6.1 什么时候才使用

只有以下情况之一成立，并且已明确决定立即影响正式服时，才使用紧急发布：

- 正式服严重故障或大面积不可用。
- 已发布版本造成秒级对局延迟、登录失败或关键功能不可用。
- 无法等到下一个零点，且继续等待造成的损失明显更大。

紧急发布可能重启服务并中断在线连接，不享受正常零点流程的一小时排空保护。

### 6.2 紧急发布前仍然必须完成

1. 确认当前分支是 `main`，工作区没有无关或未提交改动。
2. 确认将发布的完整提交号，并核对它属于 `origin/main`。
3. 运行受影响功能测试，以及两项发布链路专项回归。
4. 条件允许时先用 `deploy-test.ps1` 部署并快速验证测试服。
5. 确认紧急入口仍包含三项生产构建环境变量，且 WebSocket 顺序仍为直连优先。

执行：

```powershell
.\deploy-hk.ps1 -Emergency
```

只有确实需要前后端全部重建时才加：

```powershell
.\deploy-hk.ps1 -Emergency -All
```

紧急发布完成后，必须立即执行第 5 节的全部验收，尤其是实际 WebSocket 端点、RTT、首页刷新和静态资源来源。脚本最后显示首页 HTTP 200 不能代表低延迟验收通过。

## 7. 故障判断与处置

| 现象 | 优先检查 | 典型原因 | 处置原则 |
| --- | --- | --- | --- |
| 首页正常但对局延迟很高 | 浏览器实际 WS URL、RTT 和操作往返 | 回退到了 Cloudflare，或源站出口拥塞 | 先确认直连优先顺序，再检查网络整形与出口占用 |
| 首页刷新后空白 | `/_next/static` JS/CSS 的域名、状态码和版本 | 关键资源被切到静态域或新旧缓存不一致 | 保持 Next.js 关键资源主站同源，禁止恢复全局 `assetPrefix` |
| 卡图慢但对局正常 | `assets.grand-umi.com`、CDN 缓存和资源状态码 | 静态域、缓存或预热问题 | 不要因为卡图问题盲目重启对局后端 |
| 发布后更新日志仍旧 | 首页动态响应、无痕访问和部署提交号 | 旧 HTML 或旧前端构建仍被复用 | 先核对正式服提交与资源版本，不要只清浏览器缓存后宣布正常 |
| 发布任务没有执行 | 自动发布服务日志和三个状态文件 | 仍有在线连接、批准与测试版本不一致、提交非后继 | 按日志修正前置条件，禁止绕过门禁或强制断开玩家 |
| HTTP 200 但玩家反馈卡顿 | WS P95、实际线路和操作往返 | HTTP 健康检查未覆盖实时链路 | 直接按网络异常调查，HTTP 200 不作为反证 |

### 7.1 自动回滚与人工恢复

- 正常发布脚本在新后端无法启动、就绪检查失败、版本不匹配或新前端无法启动时，会尝试恢复旧构建。
- 如果服务显示正常，但发布后出现功能或网络回归，先记录正式服提交号、浏览器实际 WS URL、延迟样本和发布服务日志。
- 需要恢复旧逻辑时，应针对已确认的坏提交创建可追溯的回退提交，重新测试并部署测试服；故障严重时再经紧急发布入口发布该回退提交。
- 禁止在正式服仓库执行 `git reset --hard`、直接覆盖未知文件、手工拼接新旧 `.next`，或在没有版本记录的情况下替换发布目录。

## 8. 永久禁止回退的配置

以下任一变化都可能复现已经踩过的坑：

- 把 `wss://grand-umi.com/ws` 恢复为正式服首选线路。
- 删除 `wss://direct.grand-umi.com/ws` 的首选或自动回退逻辑。
- 让正常发布和紧急发布使用不同的生产构建环境变量。
- 使用 Next.js `assetPrefix` 把关键 JS/CSS 整体切到 `assets.grand-umi.com`。
- 让卡图等大体积资源重新与实时对局流量共用同一源站入口。
- 删除首页的动态响应约束，使版本入口 HTML 被长期共享缓存。
- 取消 BBR、MTU 探测、HTB/fq 或网络配置的 systemd 持久化。
- 提高资源预热并发或取消限速，却不进行在线对局带宽验证。
- 仅凭首页 HTTP 200 就宣布正式发布成功。
- 在脏工作区使用发布脚本的 `-Commit` 参数，把无关改动一并提交。
