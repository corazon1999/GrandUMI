# OP15 网络匹配对战 验收方案

> 本次实现的目标：在 GrandUMI 客户端/服务端实现 OP15 卡牌的网络匹配对战完整链路（卡组校验 → 匹配/房间 → 引擎结算 → 战斗 → 触发 → 效果 → 观战 + 回放 + 断线重连）。
>
> 总体架构：服务端 C# 权威结算 + 客户端只读镜像 + 原子效果库 + DSL（80% 卡）+ 手写脚本（复杂卡）。
>
> 验收时按 M0 → M6 顺序逐项验，任何一项失败即说明对应模块需修复。

---

## 验收准备

### 1. 启动

按你的全局快捷指令：在主聊天里说"启动GRANDUMI客户端和服务器"，会在两个 PowerShell 窗口分别启动：
- 服务端：`dotnet run`（监听 `ws://localhost:8080/ws/`）
- 客户端：`npm run dev`（默认 `http://localhost:3000`）

### 2. 编译与测试一键验证

```powershell
# 服务端编译 + 测试
dotnet build "D:\Self\GrandUMI\服务端WebSocket"
dotnet test  "D:\Self\GrandUMI\服务端WebSocket.Tests"
# 预期：编译 0 错误；测试 7 通过

# 客户端类型检查
cd "D:\Self\GrandUMI\opcgpro-web"
npx tsc --noEmit
# 预期：无输出（无错误）
```

### 3. 端到端冒烟测试

服务端运行中时执行：
```powershell
node "D:\Self\GrandUMI\tools\e2e\op15-match.mjs"
```
预期：终端打印"匹配成功 → 进入第 1 回合 → A 投降 → 双方收到 GameOver"，最后输出"✓ 测试通过"。

### 验收点

| # | 操作 | 预期 |
|---|------|------|
| 1 | 两位玩家匹配成功 | 双方收到 `MsgMatchFound` + `MsgGameStart` + 首份 `MsgGameState`（包含双方完整 PlayerSnapshot） |
| 2 | 检查 PlayerSnapshot | 己方 `handCardNumbers` 有 5 张卡号；对手 `handCardNumbers` 为 `[]`、`handCount=5` |
| 3 | 双方 mulligan 完成 | 第二份 `MsgGameState` 中 `mulliganBothDone=true`、`turnCount=1`、`phase="Main"`、`currentTurn` 仅一方为 true |
| 4 | 客户端 ws 断开（关闭浏览器 tab） | 对手收到 `MsgPlayerDisconnected gracePeriodSeconds=90` |
| 5 | 90 秒内重连（同账号登录） | 服务端 `GameRoomManager.TryReclaim` 成功，对手收到 `MsgPlayerReconnected`，重连方收到 Resync 快照 |
| 6 | 90 秒后未重连 | 服务端 `ForceGameOver`，对手收到 `MsgGameState isGameOver=true winnerIsMe=true` |
| 7 | `npx tsc --noEmit` | 无错误（旧 deprecated API 调用已全部移除） |

### 验收点

| # | 操作 | 预期 |
|---|------|------|
| 1 | 主要阶段，选 1 张手牌点击"出牌" | 服务端校验费用 → 角色登场，新 `MsgGameState` 中己方 `handCardNumbers` -1 / 场上 +1 / `costActive` -=cost |
| 2 | 第 1 回合攻击 | 服务端拒绝：`MsgActionRejected reason="第 1 回合不能战斗"` |
| 3 | 第 2 回合后宣言攻击对方领袖 | 攻击者横置，对方无【阻挡者】时直接进入伤害；战胜则触发生命牌流程 |
| 4 | 关闭"防触发信息泄露"，攻击使对方生命牌被翻 | 仅有【触发】的牌弹窗；无触发的直接进手牌 |
| 5 | 开启"防触发信息泄露"（settingsStore + MsgUpdateSettings） | 所有被翻的生命牌都弹"是否发动触发"窗口，对手只能看到`pendingPrompt` 在选择 |
| 6 | 投降 | 服务端 `WinnerIndex` 置为对方，双方收到 `MsgGameState isGameOver=true` |
| 7 | 卡组耗尽（抽空后再抽） | `WinnerIndex` 置为对方，理由 "卡组耗尽" |

## 已知后续工作（未在此次范围）

下面这些项目方案中归入"M5 全量手写卡"和"M6 完整观战回放体验"，由于工作量超出单轮实现范围，已搭好框架，按需逐张/逐功能补充：

1. **OP15 剩余 ~35 张复杂卡脚本**：每张按 OP15_001_Krieg.cs / OP15_003_Apis.cs 风格补一个 IScriptedEffect 类即可，无需改框架。
2. **DSL 词法扩展**：当前覆盖 ~25 张，方案承诺 80 张。每多支持一种文本模式（如"丢弃 N 张手牌后 KO"），加一个 op 进 DslInterpreter，无需改卡的 JSON 描述。
3. **PreKO 钩子**：让 OP15-003 等置换效果真正阻止 KO，需 BattleEngine.KOCard 改为可拦截。
4. **期限效果完整自动失效**：UntilNextOpponentEndPhase 在 TurnEngine.EnterEndPhase 中按持有者扫描清理。
5. **观战权限/回放 API**：当前 `/spectate` 直接进，建议后续加房主创建房间时"是否允许观战"勾选；`/replay/[id]` 当前期望 `/api/replay/{id}` 端点，需要 Next.js API 路由或服务端 HTTP 暴露 jsonl 文件。
6. **客户端动画效果**：M2-M5 都靠 `lastAction + actionPayload` 字段驱动，UI 上的攻击连线、KO 动画、伤害飞字等当前为占位。
7. **更多 e2e scenarios**：op15-match.mjs 当前是 1 个 scenario，方案承诺 10 个，框架已就绪，新增只需写新的 mjs 文件。
